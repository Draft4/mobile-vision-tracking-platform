# 小型化移动视觉识别与跟踪平台

## 1. 项目划分

项目主要分为底盘、云台、视觉三个子系统：

- **底盘**：负责整车运动控制、循迹、编码器采集和底盘状态上报。
- **云台**：负责俯仰/偏航运动控制、执行视觉给出的跟踪指令，并完成目标对准。
- **视觉**：负责图像采集、靶标和无人机识别、目标定位、跟踪与误差输出。

三个子系统之间的通信协议、坐标系、数据单位和状态机定义统一存放在 `interface/`，不得只写在某个子系统的代码中。

## 2. 目录结构

```text
mobile-vision-tracking-platform/
├── README.md              # 仓库总览、协作规则与目录说明
├── .gitignore             # 不进入 Git 的大文件、构建产物和本地文件规则
├── chassis/               # 底盘子系统
├── gimbal/                # 云台子系统
├── vision/                # 视觉子系统
├── interface/             # 子系统接口、通信协议和坐标系定义
├── mechanical/            # 整机机械结构与加工资料
├── config/                # 跨子系统的整机配置
├── docs/                  # 项目级设计与使用文档
├── tests/                 # 跨模块和整机集成测试
└── tools/                 # 开发、烧录、标定和日志分析工具
```

### `chassis/`

存放底盘相关的 MCU 工程、驱动代码、控制算法、引脚定义、底盘硬件说明和模块测试。后续可按实际工程拆分为 `firmware/`、`electronics/` 和 `tests/` 等子目录。

不得在这里保存仅供云台或视觉使用的代码；跨模块数据定义应放入 `interface/`。

### `gimbal/`

存放云台 MCU 工程、电机驱动、姿态或编码器读取、PID 控制、限位保护和云台标定代码。后续可按实际工程拆分为 `firmware/`、`electronics/` 和 `tests/` 等子目录。

视觉到云台的误差数据格式和控制权边界必须记录在 `interface/` 中。

### `vision/`

存放相机采集、图像处理、目标检测、目标跟踪、坐标解算和通信输出相关内容。

- `vision/src/`：可执行程序、算法模块和公共视觉代码。
- `vision/configs/`：相机、检测器、跟踪器等视觉专用配置；配置中不得包含密码、令牌或个人绝对路径。
- `vision/models/`：存放模型说明和版本记录。模型权重由 `.gitignore` 排除，通过网盘或群文件共享，不提交到 Git。

数据集原则上不提交到本仓库；应在文档中记录其来源、许可、目录约定和获取方式。

### `interface/`

存放底盘、云台和视觉之间共同遵守的接口定义，例如：

- 串口、CAN 或其他通信协议；
- 数据帧结构、消息编号、校验方式和超时机制；
- 坐标系方向、角度正负、单位、时间戳和精度；
- 目标发现、跟踪、丢失、搜索和故障状态机；
- 各子系统启动顺序、心跳和版本兼容规则。

当前公共约定见：[坐标系与方向约定](interface/coordinate-system.md)。

接口发生不兼容修改时，必须由受影响模块的负责人共同评审，并在同一次提交或合并请求中同步更新文档和相关实现。

### `mechanical/`

存放整机装配、底盘和云台结构件、相机支架、工程图、STEP/STL 文件、加工参数和 BOM。文件名应体现部件名称和版本，例如 `camera_mount_v2.step`。

CAD、三维模型和其他大型工程文件由 `.gitignore` 排除，通过网盘或群文件共享。可由源文件重新生成的临时文件也不应提交。

### `config/`

存放跨子系统使用的整机级配置，例如设备编号、通信端口映射、整机工作模式和默认参数组合。视觉内部参数应放入 `vision/configs/`。

建议提交可直接复制的示例配置，例如 `robot.example.yaml`；包含本机路径或敏感信息的实际配置不得提交。

### `docs/`

存放项目级文档，例如总体架构、硬件接线、环境搭建、烧录方法、标定流程、调试记录、实验结果、里程碑和重要技术决策。

建议使用 Markdown 保存可长期维护的说明。临时聊天记录和无法说明背景的截图不应直接作为正式文档。

### `tests/`

存放跨模块通信测试、整机集成测试、回归测试、测试数据说明和验收脚本。只属于单个模块的单元测试可以放在对应模块内部。

每项关键功能应尽量给出可重复的测试条件、操作步骤、预期结果和实际结果。

### `tools/`

存放烧录、串口调试、相机标定、日志解析、数据转换、模型导出和开发环境辅助脚本。工具需要说明运行环境和使用方法，不得依赖未记录的个人电脑路径。

## 3. 各目录 README 维护规则

每个目录中的 `README.md` 由对应项目的同学共同维护。初始文件可以为空，但目录开始放入有效内容时，应同时补充 README，至少说明：

1. 目录用途和负责范围；
2. 项目负责人、维护者；
3. 硬件、软件及工具链版本；
4. 构建、烧录或运行方法；
5. 输入、输出以及与其他模块的依赖；
6. 参数配置和标定方法；
7. 测试方法、当前状态和已知问题；
8. 第三方资料的来源与许可证。

出现下列情况时，必须在同一次提交中更新对应 README：

- 新增、删除或移动目录中的重要文件；
- 构建、烧录、运行或标定步骤发生变化；
- 硬件接线、引脚、通信接口或配置格式发生变化；
- 引入新的依赖、模型、开发板或工具链版本；
- 已知问题、模块状态或负责人发生变化。

README 应描述当前可用状态，不要只记录最初方案。较长的设计过程和实验报告可放入 `docs/`，并从模块 README 链接过去。

## 4. 分支与协作方式

协作时需要做到：不要覆盖别人的工作、让 `main` 保持基本可用、让其他人能够看懂修改内容。

### 4.1 分支怎么用

仓库长期保留一个主分支：

- `main`：保存大家已经完成并愿意共同使用的版本。

开发代码时，建议从 `main` 新建一个短期分支。分支名称不需要严格套用格式，使用“小写英文类别/简短说明”并且自己能看懂即可：

- `feature/vision-target`：增加视觉靶标识别；
- `fix/gimbal-shake`：修复云台抖动；
- `docs/wiring`：补充接线说明；
- `test/serial-link`：调试串口联动。

如果不确定类别，直接使用 `work/姓名-任务` 也可以，例如 `work/zhangsan-camera`。不要使用只有 `test`、`new` 或 `final` 这类无法判断内容的名字。

创建分支的基本操作如下：

```bash
git switch main
git pull
git switch -c feature/vision-target
```

以下情况建议使用独立分支：

- 要修改程序代码、接口、硬件配置或机械文件；
- 一项工作需要持续几天；
- 多个人可能同时修改相同文件；
- 还不确定修改能否正常运行。

只改错别字、补充几句话等很小的文档修改，可以在提前告知队友后直接提交到 `main`。不要向 `main` 强制推送，也不要随意改写已经共享的提交历史。

### 4.2 日常协作步骤

一次普通开发可以按照下面的流程进行：

1. 开始工作前执行 `git pull`，获取队友的最新修改；
2. 新建自己的任务分支；
3. 完成一小段可以说明清楚的工作后提交一次；
4. 推送分支，并在群里说明做了什么、是否已经测试；
5. 确认没有明显问题后合并到 `main`；
6. 合并后其他成员再次执行 `git pull`。

第一次推送新分支可以使用：

```bash
git push -u origin feature/vision-target
```

尽量不要多人共用同一个开发分支。如果必须共同修改同一个文件，先在群里简单说明各自修改的区域，减少冲突。

## 5. 提交要求

提交信息不强制使用 Conventional Commits。推荐使用容易理解的中文或英文短句，格式为：

```text
模块: 做了什么
```

例如：

```text
vision: 增加红色靶标中心检测
gimbal: 修复偏航编码器溢出问题
chassis: 调整左轮速度环参数
docs: 补充系统接线说明
```

提交时不要求每次修改都非常小，也不要求提交历史十分整齐，但建议在完成一个可说明的步骤后及时提交，避免几天的工作只留下一个巨大提交。在个人开发分支上可以使用 `WIP: 云台串口调试中` 这样的临时提交；合并前确保队友能够理解当前状态即可。

提交前至少完成以下检查：

- 执行 `git status`，确认没有误选无关文件；
- 能编译或运行时，进行一次基本验证；暂时无法测试时，在提交或合并说明中写明；
- 修改接口、接线、启动步骤或配置格式时，顺手更新相应 README；
- 不提交密码、访问令牌、无线网络信息和个人敏感信息；
- 不提交来源不明的代码、模型、数据集或素材；
- 模型、视频、数据集、CAD 和三维工程文件通过网盘或群文件共享，不使用 Git LFS，也不提交到普通 Git 历史。

编译产物、缓存、日志和 IDE 个人配置原则上不提交。如果某个自动生成文件确实是工程运行所必需的，可以提交，但应在对应 README 中说明。

### 5.1 大文件共享规则

根目录的 `.gitignore` 已默认排除常见模型权重、数据集、视频、压缩包、CAD/三维工程文件和编译产物。团队成员下载这些文件后，仍可把它们放在项目约定的目录中使用，只是 Git 不会追踪它们。

为避免网盘或群文件中的版本混乱，在对应模块的 README 中至少记录：

- 文件名和用途；
- 文件版本或导出日期；
- 应放置的项目相对路径；
- 分享位置或群文件名称；
- 提供者；
- SHA-256 校验值（重要模型或工程文件建议填写）。

例如：

```text
文件：target_detector_v2.onnx
用途：靶标检测模型
放置位置：vision/models/target_detector_v2.onnx
分享位置：项目群文件/视觉模型/target_detector_v2.onnx
提供者：张三
SHA-256：待填写
```

如果某个被忽略的文件后来确实需要进入 Git，应先修改 `.gitignore` 并和队友说明原因，不建议直接使用 `git add -f` 绕过规则。

## 6. 合并方式

合并请求（Pull Request 或 Merge Request）是推荐做法，但不作为所有修改的硬性要求：

- 只影响自己负责模块的小改动，可以在完成基本测试后自行合并；
- 影响多个模块、通信协议、坐标系、公共配置或整机接线的修改，应让相关同学先看一下；
- 还没有运行成功的代码不要直接合入 `main`。确实需要提前共享时，保留在开发分支，并在 README 或群里说明当前问题；
- 如果拿不准是否会影响别人，先发起合并请求或在群里询问。

合并前建议先把最新的 `main` 合入自己的分支：

```bash
git switch main
git pull
git switch feature/vision-target
git merge main
```

如果出现冲突，不要随意删除冲突内容或强行覆盖远端。先确认双方修改的目的；无法判断时，请对应文件的修改者一起处理。解决冲突并完成基本测试后，再推送并合并。

合并前用下面的简化清单检查即可：

- [ ] 其他人能够从提交信息或说明中看懂这次修改；
- [ ] 已完成基本运行或编译检查，或者明确写出了尚未测试的部分；
- [ ] 没有误提交敏感信息、临时文件和不必要的大文件；
- [ ] 如果修改会影响其他模块，已经通知相关成员；
- [ ] 新增第三方资料时，已经记录来源和许可证。

合并完成并确认不再使用后，可以删除对应开发分支。是否压缩提交、选择哪种合并按钮不作统一要求，以简单、不会丢失代码为准。

## 7. 建议实施顺序

1. 复现原项目的靶标识别、底盘运动和云台对准功能；
2. 固化三个子系统的通信协议、坐标系和标定流程；
3. 建立可重复的整机联调与回归测试；
4. 增加无人机数据采集、识别与跟踪能力；
5. 优化实时性、丢失重捕获、运动预测和整机稳定性。
